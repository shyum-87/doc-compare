## 1. 목적과 위치

이 시스템은 기준 문서(한국어 SOP, Spec)에서 체크리스트를 만들고, 외주사·법인 문서(베트남어, 영어, 중국어)가 체크리스트의 모든 항목을 반영했는지 항목별로 판정한다(D-012).

단위 ①은 그 앞 단계다. 기준 문서와 대상 문서를 **위치를 가리킬 수 있는 요소 목록**으로 읽고, 읽은 결과를 믿을 수 있는지 점검한다. 체크리스트 추출(단위 ③)과 판정(단위 ④)은 이 요소 목록을 입력으로 받는다.

| 순서 | 하는 일 | 단위 |
|---|---|---|
| 1 | 기준 문서와 대상 문서를 요소 목록으로 읽는다 | ① |
| 2 | 기준 문서에서 체크리스트 초안을 뽑고, 원문 전체를 덮었는지 확인한다 | ③ |
| 3 | 사람이 체크리스트를 승인하고 버전을 고정한다 | ③ |
| 4 | 항목마다 대상 문서에서 근거를 찾아 판정한다 | ④ |
| 5 | 결과를 보여 준다 | ⑤ |

## 2. 범위

### 만드는 것

- 프로젝트 뼈대: `pyproject.toml`, `app/`, `tests/`, `config/example.env`, `.gitignore`, `.gitattributes`
- 문서 모델(`app/models/`)
- 줄 단위 파서(`app/parsing/`). `rag_ko.md`와 `rag.md`를 같은 파서로 읽는다.
- 번역본 점검: 대상 문서 한 건의 원문(`rag.md`)과 번역본(`rag_ko.md`)에서 숫자·단위·코드가 같은지 확인한다.
- 품질 점검: 발견 항목 목록과 결과 상태
- 명령줄 `python -m app.parsing`: 결과를 JSON 파일로 쓴다.

### 만들지 않는 것

LLM 호출, 체크리스트 추출, 판정, UI, API, DB, 원본 DOCX/PDF 읽기, 서식 검사, 이미지 파일 읽기, 발견 항목을 해제하는 절차.

### 완료 기준

1. 제빵 샘플(`tests/fixtures/rag_ko/sample_bakery_sop.md`)이 요소 49개로 읽힌다: 페이지 마커 4(8~11), 헤딩 6, 표 5, 이미지 3, 목록 항목 14, 문단 17, 미분류 0.
2. 모든 요소가 페이지, 절 경로, 원본 줄 번호를 갖는다. 표의 셀은 표 순번, 행, 열을 더 갖는다.
3. 빈 줄이 아닌 모든 줄이 정확히 한 요소에 속한다.
4. 샘플의 오탈자(`합께`, `패덜`)가 그대로 남는다.
5. 번역본에서 숫자 하나를 바꾸거나 표의 행 하나를 지우면 품질 점검이 그 요소를 짚는다.
6. 깨진 입력(빈 파일, 페이지 마커 없음, 열 수 불일치)에서 프로그램이 죽지 않고, 정상 결과처럼 통과시키지도 않는다.

## 3. 입력

| 문서 | 파일 | 언어 |
|---|---|---|
| 기준 문서 | 한국어 Markdown 1개 | `ko` |
| 대상 문서 | `rag_ko.md`(한국어 번역본) + `rag.md`(번역 전 원문) | 번역본 `ko`, 원문 `vi` / `en` / `zh` |

파일 형식은 [RAG_KO_FORMAT.md](../../RAG_KO_FORMAT.md)를 따른다. 파서 JSON은 쓰지 않는다(D-007).

파일을 읽을 때 UTF-8로 해석한다. 앞머리 BOM은 무시하고, 줄 끝은 CRLF·LF·홀로 있는 CR을 모두 받는다. 그 밖의 문자(세로 탭, 폼 피드, U+0085, U+2028 등)는 줄을 나누지 않는다. 줄 번호는 사람이 편집기에서 보는 번호와 같아야 한다. `sha256`은 파일 바이트 그대로 계산한다.

## 4. 문서 모델

Pydantic 모델이며 만들어진 뒤에는 바꿀 수 없다(frozen). 번역본 점검과 품질 점검의 결과는 문서 안에 넣지 않고, `element_id`로 문서를 가리키는 별도 객체로 둔다.

### 4.1 문서

| 필드 | 내용 |
|---|---|
| `doc_id` | 문서 식별자. 실행할 때 사람이 넣는다. |
| `version` | 문서 버전. 실행할 때 사람이 넣는다. |
| `variant` | `translated`(한국어 번역본) 또는 `source`(번역을 거치지 않은 파일) |
| `language` | `ko`, `vi`, `en`, `zh` |
| `file_name` | 파일 이름. 경로는 넣지 않는다. |
| `sha256` | 파일 바이트의 해시 |
| `elements` | 요소 목록. 파일에 나온 순서대로이며 중첩하지 않는다. |

원문과 번역본은 서로 다른 문서 객체다. 한국어 기준 문서는 `variant = source`, `language = ko`인 문서 하나다.

### 4.2 요소

공통 필드:

| 필드 | 내용 |
|---|---|
| `element_id` | 순번으로 만든다. `e0001`부터 시작한다. |
| `kind` | 아래 일곱 가지 중 하나 |
| `locator` | `page`, `section_path`, `line_start`, `line_end` |
| `raw` | 원본 줄 그대로 |
| `text` | 표기 기호만 걷어 낸 본문. 글자는 바꾸지 않는다. |

종류별 필드:

| `kind` | 추가 필드 |
|---|---|
| `page_marker` | `page` |
| `heading` | `level`, `number`(조항 번호, 없으면 비움), `title` |
| `paragraph` | 없음 |
| `list_item` | `marker`(파일에 적힌 그대로) |
| `table` | `table_index`, `header`, `rows` |
| `image` | `image_id`, `file_name`, `title`. 항상 "읽지 못한 영역"이다. |
| `unclassified` | 없음 |

표의 셀은 `row`, `col`, `text`를 갖는다. 행과 열은 1부터 세고, 머리글 행은 0행이다. 셀은 `e0017:r2c3`처럼 요소 ID + 행 + 열로 가리킨다. `table_index`는 문서 안에서 표가 나온 순번이며 1부터 센다.

예(제빵 샘플의 3.2 표):

```json
{
  "element_id": "e0017",
  "kind": "table",
  "locator": {"page": 9, "section_path": ["3", "3.2"], "line_start": 36, "line_end": 42},
  "table_index": 2,
  "header": ["확인 항목", "확인 방법", "판정기준"],
  "rows": [[{"row": 1, "col": 1, "text": "품번"}, "…"]]
}
```

### 4.3 위치 정보

- **`page`:** 가장 최근 페이지 마커의 숫자다. 첫 마커 앞의 요소는 비워 둔다.
- **`section_path`:** 상위 헤딩부터 자기 절까지의 조항 번호 목록이다(예: `["3", "3.2"]`). 조항 번호가 없는 헤딩은 제목을 넣는다. 경로는 헤딩 단계(`#`의 수)를 따라 만든다.
- **`line_start`, `line_end`:** 파일의 줄 번호이며 1부터 센다.

모델은 있을 수 없는 위치를 받지 않는다. 줄 번호가 1보다 작거나 `line_end`가 `line_start`보다 앞이면 거부한다. 빈 `element_id`, 한 문서 안에서 겹치는 `element_id`, 자기 자리와 다른 `row`·`col`을 가진 셀도 거부한다. `page`는 파일에 적힌 숫자를 그대로 담으므로 범위를 제한하지 않는다.

### 4.4 한계

요소 ID는 순번이므로 파일이 바뀌면 같은 ID가 다른 요소를 가리킨다. 요소 ID를 쓰는 모든 결과는 문서의 `sha256`과 함께 저장한다.

## 5. 파싱 규칙

범용 Markdown 파서를 쓰지 않고 줄 단위로 직접 읽는다(D-010). 줄마다 아래 규칙을 위에서부터 적용하고, 처음 맞는 규칙으로 정한다.

| 순서 | 규칙 | 조건 |
|---|---|---|
| 1 | 빈 줄 | 요소를 만들지 않는다. |
| 2 | 페이지 마커 | 줄 전체가 `[PAGE 9]` 또는 `[PAGE9]`다. 숫자를 읽는다. 숫자는 ASCII 숫자 1~6자리다. `[PAGE`가 들어 있는데 줄 전체가 마커가 아니면 미분류다(아래 "가리는 문자"). |
| 3 | 헤딩 | `#` 1~6개 + 공백 + 제목. 제목 앞의 `3.`, `3.2`는 조항 번호로 떼어 낸다. 번호는 `**`를 벗긴 제목에서 읽고 ASCII 숫자만 인정한다. 가리는 문자나 `*`가 번호를 바꾸면 미분류다(아래). |
| 4 | 표 | `\|`로 시작하는 줄이 이어지고 둘째 줄이 `\|---\|---\|` 형태다. 그런 줄이 묶음 안에 또 있으면 표가 아니다(§5.1). |
| 5 | 이미지 | 줄 전체가 `![img021](<img021.png "제목">)` 또는 표준형 `![a](f.png "제목")`이다. 이미지 ID와 파일 이름이 모두 있어야 한다. 다른 요소 안에 적힌 이미지는 §5.2. |
| 6 | 목록 항목 | `1)`, `1. `, `- `, `* `, 공백 없는 `-글자`로 시작한다. 번호의 숫자는 어느 문자 체계든 받고 표시는 적힌 그대로 둔다. 정하지 않는 경우는 §5.2. |
| 7 | 문단 | 위에 해당하지 않는 줄. **한 줄이 한 문단**이며 이어진 줄을 합치지 않는다. |
| 8 | 미분류 | 구조처럼 보이지만 위 규칙에 맞지 않는 줄 |

미분류로 두는 줄: 구분 줄이 없거나 둘째 줄 말고 다른 줄에도 있는 `|` 묶음의 줄, 형식이 어긋났거나 ID나 파일 이름이 빈 `![…`, 형식이 어긋난 `[PAGE x]`, 공백 없는 `##제목`, 코드 펜스, 구분선(`---`, `***`, `___`, 공백을 둔 `- - -`), HTML 태그 줄과 `<!--` 줄, `>` 인용, `-` 뒤에 보이는 글자가 없는 줄(`-`, `--`, `-*`), 그리고 §5.2에서 미분류로 둔다고 적은 줄.

**가리는 문자.** 스스로는 아무것도 그리지 않아 `[PAGE 9]`나 `### 3.1`을 규칙에서 가릴 수 있는 문자다. 가려진 표시를 문단으로 읽으면 그 뒤 요소의 쪽과 절 위치가 소리 없이 틀린다. 아래 중 하나인 문자를 가리는 문자로 본다. 탭만 예외다.

- 유니코드 범주 Cc·Cf: 제어 문자, BOM, 폭 없는 공백, 방향 표시
- 유니코드 범주 Cn: 문자가 배정되지 않은 코드 포인트
- 유니코드 범주 Mn·Me: 결합 문자
- 빈칸으로 그려지는 글자 다섯 개: U+115F, U+1160, U+3164(한글 채움 문자), U+FFA0, U+2800

공백류(범주 Zs: 공백, 줄바꿈 없는 공백, 전각 공백 등)는 눈에 보이는 간격이라 넣지 않는다. 사용자 지정 영역(Co)은 글꼴이 글리프로 그리므로(PDF에서 온 글머리표 등) 넣지 않는다. 미배정(Cn)은 넣는다. 미배정 여부는 파이썬의 유니코드 버전에 따라 달라지므로, 새 유니코드에서만 배정된 문자로 시작하는 줄은 옛 파이썬에서 미분류가 된다. 소리 없이 틀리는 것보다 드러나는 쪽을 택한다.

- 앞뒤 공백을 뗀 줄이 가리는 문자로 시작하면 규칙 2~7을 적용하지 않고 미분류로 둔다.
- 줄 가운데에 다른 도구가 줄바꿈으로 보는 문자(세로 탭, 폼 피드, U+001C~U+001E, U+0085, U+2028, U+2029)가 있으면 규칙 2~7을 적용하지 않고 미분류로 둔다. 읽을 때 이 문자들은 줄을 나누지 않으므로(§3), 그 뒤에 온 헤딩이나 표가 문단 안에 묻힐 수 있다. 줄 끝에 붙은 그런 문자는 공백처럼 떼어 낸다(쪽 나눔이 남긴 폼 피드 뒤의 `[PAGE 9]`는 페이지 마커다). 표 안의 줄도 같다(§5.1).
- `[PAGE`는 예약된 표시다. 가리는 문자·`*`·공백을 빼고 대소문자 구분 없이 봤을 때 `[PAGE`가 들어 있는 줄은 줄 전체가 페이지 마커(규칙 2)이거나, 아니면 미분류다. `**[PAGE 9]**`, 안쪽에 폭 없는 공백이 낀 `[PAGE 9]`, 본문 끝에 붙은 `…다.[PAGE 9]`, 문장 안의 `[Page 3]`이 모두 미분류다. 표의 둘째 줄부터는 규칙 4가 먼저 가져가므로 이 검사를 받지 않는다.
- 헤딩에서 읽은 조항 번호는 가리는 문자와 `*`를 모두 뺀 글에서 읽은 번호와 같아야 한다. 다르거나, `*`와 공백 뒤 첫 글자가 가리는 문자면 그 줄은 미분류다. `### **<폭 없는 공백>**3.1 조회`, `### *3.1* 조회`, `### ** 3.1 조회 **`가 모두 미분류다. 낱말 안의 결합 문자(분해형으로 적힌 베트남어 등)와 번호에서 떨어진 가리는 문자는 그대로 둔다.
- 생김새만 비슷한 표시(전각 `［PAGE 9］`, `【PAGE 9】`, 번역된 `[페이지 9]` 등)는 접어서 읽지 않고 문단으로 둔다. 단위 ①에서는 다루지 않는다.

문자를 지우고 해석하는 것은 추측이므로 하지 않는다. 파일 맨 앞의 BOM 하나는 읽을 때 이미 떼어 낸다.

### 5.1 표

- 줄 앞뒤 공백을 떼고, 맨 앞과 맨 뒤의 `|`를 뗀 뒤 `|`로 나눈다. `\|`는 나누지 않는다. 셀 앞뒤 공백을 뗀다.
- 셀 안의 `<br>`은 줄바꿈으로 바꾼다.
- 열 수가 머리글과 다른 행은 읽은 그대로 두고 발견 항목으로 표시한다. 채우거나 잘라 내지 않는다.
- 구분 줄은 적힌 그대로의 셀이 모두 `-` 하나 이상(앞뒤에 `:` 가능)인 `|` 줄이다. `**---**`처럼 굵게 적힌 대시는 구분 줄의 셀이 아니다.
- 구분 줄이 둘째 줄 하나뿐인 묶음만 표로 읽는다. 첫 줄이든 셋째 줄 뒤든 다른 줄이 구분 줄이면 줄마다 미분류로 둔다. 표 두 개가 빈 줄 없이 붙었거나 머리글이 빠졌을 수 있고, 어느 쪽인지는 추측이다. 셀이 모두 `-`뿐인 머리글이나 데이터 행(`| - | - |`)도 구분 줄로 본다.
- 줄 가운데에 다른 도구가 줄바꿈으로 보는 문자(§5에 적은 세로 탭, 폼 피드 등)가 있는 `|` 줄은 표에 넣지 않는다. 표는 그 앞 줄에서 끝나고 그 줄은 미분류다. 그 뒤의 `|` 줄은 새 묶음으로 다시 본다.

### 5.2 추측하지 않는 지점

| 상황 | 처리 |
|---|---|
| 공백 없는 `-` 뒤에 숫자가 온다(예: `-18℃ 이하로 보관`, `-**18℃**`, `-.5 kg`) | 목록인지 음수인지 정할 수 없다. 문단으로 두고 `-`를 지우지 않으며 발견 항목으로 표시한다. `*`와 공백은 건너뛰고 보며, `.`이나 `,` 뒤의 숫자도 같다(그 사이의 가리는 문자는 없는 것으로 본다). 숫자는 유니코드 숫자 범주의 문자다(전각 숫자, `½`, `①` 포함. 숫자를 뜻하는 한자 `三`은 글자라서 아니다). |
| 목록 표시(`1)`, `1.`, `-`, `*`)와 처음 보이는 글자 사이에 가리는 문자(§5)가 있다 | 표시가 무엇인지, `-`가 숫자의 부호인지가 보이지 않는 문자에 달린다. 미분류로 둔다. |
| `숫자.` 뒤의 본문이 다시 `숫자.`와 공백(또는 줄 끝)으로 시작한다(예: `2024. 5. 1 개정`, `1. 2. 항목`) | 날짜나 숫자 나열일 수 있다. 앞 숫자를 목록 번호로 떼어 내지 않고 미분류로 둔다. 본문은 `*`와 가리는 문자를 빼고 본다. `2. 5 kg 투입`처럼 뒤 숫자에 점이 없으면 표시가 `2.`인 목록 항목이다. |
| 이미지가 헤딩, 표, 목록 항목, 문단 안에 적혀 있다(`![…](`가 들어 있다) | 그 요소는 그대로 읽고 이미지 요소로 떼어 내지 않는다. 이미지가 있는 줄마다 `IMAGE_PRESENT`를 그 요소에 붙인다. |
| 조항 번호와 헤딩 단계가 어긋난다 | 경로는 헤딩 단계를 따르고 발견 항목으로 표시한다. 상위 헤딩과 자신이 모두 조항 번호를 갖는데, 자신의 번호가 상위 번호 + `.`으로 시작하지 않으면 어긋난 것이다. |
| 첫 페이지 마커 앞에 내용이 있다 | 요소로 남기고 `page`를 비우며 발견 항목으로 표시한다. |
| 페이지 번호가 줄거나 반복된다 | 읽은 숫자를 그대로 쓰고 발견 항목으로 표시한다. 번호가 건너뛰는 것은 정상이다. |

### 5.3 `text` 만들기

짝이 맞는 `**…**`를 벗기고 `<br>`을 줄바꿈으로 바꾸는 것만 한다(`**`를 먼저 벗기므로 `<br>`을 사이에 둔 `**…**`도 벗겨진다). 오탈자, 띄어쓰기, 괄호 병기는 건드리지 않는다.

### 5.4 해석하지 않는 것

들여쓰기에 따른 목록 중첩, 문장 안의 링크와 기울임, 병합 셀.

## 6. 번역본 점검

대상 문서 한 건 안에서 원문과 번역본을 맞대는 점검이다. 기준 문서와 대상 문서의 비교가 아니다. 한국어 기준 문서에는 하지 않는다.

두 파일이 요소 단위로 1:1 대응한다고 가정한다(D-008). 이 가정은 실제 파일 쌍으로 확인하지 않았다.

### 6.1 짝짓기

1. **뼈대를 맞춘다.** 뼈대는 페이지 마커와 헤딩이다. 페이지 번호, 헤딩 단계, 조항 번호를 비교하고 제목은 비교하지 않는다.
2. **뼈대가 다르면** 표준 라이브러리 `difflib`으로 일치하는 부분을 찾는다. 일치하지 않는 부분의 요소는 짝 없음으로 둔다.
3. **뼈대 사이 구간마다** 요소의 종류가 순서대로 같으면 순번대로 1:1로 짝짓는다. 다르면 그 구간 전체를 짝 없음으로 둔다. 어느 요소가 빠졌는지 추측하지 않는다.
4. **표**는 행 수와 열 수가 같을 때만 셀끼리 짝짓는다.
5. **이미지**는 이미지 ID가 같아야 짝이 된다.

### 6.2 비교하는 토큰

짝이 된 요소(표는 셀)마다 아래 토큰을 뽑아 개수까지 비교한다. 순서는 보지 않는다.

| 토큰 | 정의 | 예 |
|---|---|---|
| 숫자 | 숫자로 시작하는 구간. 문서 언어의 표기로 값을 해석한다. | `180`, `1.0`, `1,0` |
| 단위 | 숫자 바로 뒤(공백 0~1개)에 오는, 단위 표에 있는 기호 | `℃`, `%`, `mm`, `kPa` |
| 범위·공차 기호 | `±`, `~`, 음수 부호 | `±`, `-18`의 `-` |
| 코드 | ASCII 영문자로 시작하고 숫자를 하나 이상 포함하는, 영문자·숫자·`-`·`_`의 연속 구간 | `BK01`, `WI-BK-204`, `img021` |

- **코드를 좁게 정의한 이유:** 영어와 베트남어는 라틴 문자를 쓰므로 영문 단어를 코드로 볼 수 없다(D-011). 숫자가 들어간 구간만 코드로 본다.
- **구간의 경계:** 한글, 한자, 성조 부호가 붙은 글자는 구간에 넣지 않는다. `약30분`과 `约30分钟`에서는 숫자 `30`만 나온다.
- **음수 부호:** 숫자 바로 앞의 `-`이며, 그 앞 글자가 영문자나 숫자가 아닐 때다. `WI-BK-204`와 `2026-11-11`의 `-`는 음수 부호가 아니다.
- **단위의 경계:** 단위 뒤에 라틴 문자(성조 부호가 붙은 글자 포함)가 이어지면 단위로 보지 않는다. `30 min`의 `m`은 단위가 아니다. 한글이나 한자가 이어지는 것은 허용한다(`180℃에서`, `5mm의`).
- **단위 표:** 코드 한 곳에 둔다. 처음 넣는 값은 `℃`, `°C`, `℉`, `%`, `μm`, `mm`, `cm`, `m`, `mg`, `g`, `kg`, `mL`, `L`, `Pa`, `kPa`, `MPa`, `rpm`, `ppm`이다. 실제 문서에서 더 나오면 추가한다.
- **정규화:** 비교할 때만 유니코드 NFKC로 정규화한다(전각 → 반각, `℃` → `°C`). NFKC가 바꾸지 않는 두 글자는 따로 접는다: 빼기 기호 U+2212(−) → `-`, 물결표 U+301C(〜) → `~`. 저장된 원문은 바꾸지 않는다.

### 6.3 숫자 표기

| 언어 | 소수점 | 천 단위 구분 |
|---|---|---|
| `ko`, `en`, `zh` | `.` | `,` |
| `vi` | `,` | `.` |

천 단위 구분은 뒤에 숫자가 정확히 3개 올 때만 인정한다. 그 언어의 표기에 맞는 숫자는 값으로 바꾼다(베트남어 `1,5` → 1.5, 베트남어 `1.000` → 1000).

비교 순서:

1. 양쪽 모두 자기 언어의 표기에 맞는 숫자는 **값**으로 비교한다.
2. 남은 숫자 중 한쪽이라도 표기에 맞지 않으면(베트남어 `3.2`, 한국어 `1,0`, `1.2.3`) **문자열**로 비교한다. 문자열이 같으면 일치다.
3. 그래도 남으면 불일치다. 표기에 맞지 않아 남은 숫자에는 `NUMBER_FORMAT_AMBIGUOUS`를 붙인다.

양쪽 표기에 모두 맞지만 값이 다른 경우(베트남어 `1.000` = 1000, 한국어 `1.000` = 1.0)는 문자열이 같아도 불일치다.

### 6.4 결과

- 짝 목록: 번역본 쪽 참조, 원문 쪽 참조, 상태(`match` / `token_mismatch`), 빠진 토큰, 더해진 토큰
- 짝 없는 구간 목록: 양쪽의 요소 ID 범위와 이유

### 6.5 검출하지 못하는 것

- 원본 → `rag.md` 단계의 오독과 누락
- 숫자가 없는 문장의 오역
- 한글이나 한자로 옮겨진 단위
- 한계 표현(`以下`, `dưới`, `less than`)의 뒤바뀜. 언어별 대응표는 실제 파일 쌍을 본 뒤에 만든다.
- 글자로 쓴 수(`once`, `hai lần`). 번역본에서 숫자로 바뀌면 불일치로 표시된다.

## 7. 품질 점검

문제가 생기면 멈추거나 넘어가지 않고 발견 항목으로 기록한다.

### 7.1 결과 상태

| 상태 | 조건 | 이후 단계에서의 의미 |
|---|---|---|
| `FAILED` | 문서를 만들 수 없다: 입력 파일 중 하나라도 없거나, UTF-8이 아니거나, 빈 줄뿐이거나, 내부 오류가 났다. | 이 문서에 대한 판정은 모두 UNKNOWN이다. |
| `REVIEW_REQUIRED` | 문서는 만들었고 "검토 필요" 발견 항목이 하나 이상 있다. | 걸린 요소에 의존하는 판정은 PASS가 될 수 없다. |
| `OK` | "검토 필요" 발견 항목이 없다. | 그대로 쓴다. |

문서 전체를 비율로 합격·불합격시키지 않는다. 발견 항목이 걸린 요소 단위로 막는다(D-013).

결과 모델은 상태와 내용이 어긋나는 조합을 받지 않는다. `FAILED`는 실패 사유가 있고 문서·발견 항목·번역본 점검 결과가 없어야 한다. `REVIEW_REQUIRED`와 `OK`는 실패 사유가 없고 문서가 하나 이상 있어야 하며, "검토 필요" 발견 항목이 있으면 `REVIEW_REQUIRED`, 없으면 `OK`여야 한다.

### 7.2 발견 항목

| 코드 | 내용 | 등급 | 범위 |
|---|---|---|---|
| `UNCLASSIFIED_LINE` | 어느 규칙에도 맞지 않는 줄 | 검토 필요 | 요소 |
| `AMBIGUOUS_LIST_OR_NEGATIVE` | 공백 없는 `-` 뒤에 숫자가 오는 줄 | 검토 필요 | 요소 |
| `TABLE_ROW_WIDTH_MISMATCH` | 열 수가 머리글과 다른 행 | 검토 필요 | 요소 |
| `NO_PAGE_MARKER` | 페이지 마커가 하나도 없다 | 검토 필요 | 문서 |
| `CONTENT_BEFORE_FIRST_PAGE` | 첫 마커 앞에 내용이 있다 | 검토 필요 | 요소 |
| `PAGE_NUMBER_NOT_INCREASING` | 페이지 번호가 줄거나 반복된다 | 검토 필요 | 요소 |
| `SOURCE_NOT_PROVIDED` | 번역된 문서인데 원문 파일이 없다 | 검토 필요 | 문서 |
| `SKELETON_MISMATCH` | 원문과 번역본의 페이지 마커·헤딩이 다르다 | 검토 필요 | 구간 |
| `SEGMENT_UNALIGNED` | 구간 안 요소의 종류나 개수가 다르다 | 검토 필요 | 구간 |
| `TABLE_SHAPE_MISMATCH` | 짝이 된 표의 행 수나 열 수가 다르다 | 검토 필요 | 요소 |
| `TOKEN_MISMATCH` | 숫자·단위·코드가 원문과 다르다 | 검토 필요 | 요소 또는 셀 |
| `NUMBER_FORMAT_AMBIGUOUS` | 숫자 표기를 해석할 수 없고 상대 쪽에 같은 문자열도 없다 | 검토 필요 | 요소 또는 셀 |
| `HEADING_NUMBER_MISMATCH` | 조항 번호와 헤딩 단계가 어긋난다 | 참고 | 요소 |
| `IMAGE_PRESENT` | 이미지(읽지 못한 영역)가 있다. 이미지 요소이거나, 다른 요소 안에 이미지가 적혀 있다 | 참고 | 요소 |

- 범위가 "문서"인 발견 항목은 그 문서의 모든 요소에 걸린 것으로 본다.
- 등급은 코드가 정한다. 모델은 코드와 다른 등급을 받지 않는다. 줄 범위는 시작과 끝을 함께 주며 1 이상이고 순서가 맞아야 한다.
- 발견 항목은 코드, 등급, 어느 문서인지(`translated` / `source`), 요소 ID 목록, 셀 참조(있을 때), 줄 범위, 상세(빠진 토큰과 더해진 토큰 등)를 갖는다.
- 이미지가 있는 구간에서 "근거 없음"을 어떻게 다룰지는 단위 ④에서 정한다.

### 7.3 예외와 로그

- **예상한 입력 문제**는 예외를 던지지 않고 결과 상태와 발견 항목으로 돌려준다.
- **예상하지 못한 내부 오류**는 맨 바깥에서 잡아 `FAILED`로 바꾼다. 일부만 처리된 문서를 정상 결과처럼 내보내지 않는다.
- **"모든 줄이 한 요소에 속한다"** 는 파싱 뒤 코드로 확인한다. 어긋나면 내부 오류다.
- **로그에는 문서 본문과 토큰 값을 쓰지 않는다.** 코드, 요소 ID, 줄 번호, 개수만 남긴다.

### 7.4 버전 기록

결과에 `parser_version`과 입력 파일의 `sha256`을 남긴다. 파싱 규칙이나 토큰 규칙을 바꾸면 `parser_version`을 올린다.

## 8. 명령줄

```
python -m app.parsing <주 파일> --doc-id <ID> --version <버전>
    --original-language {ko,vi,en,zh}
    [--source <rag.md>]
    --out <결과.json>
```

| `--original-language` | `--source` | 동작 |
|---|---|---|
| `ko` | 없음 | 주 파일을 한국어 기준 문서로 읽는다. 번역본 점검을 하지 않는다. |
| `ko` | 있음 | 사용법 오류다. 종료 코드 2. |
| `vi` / `en` / `zh` | 있음 | 주 파일을 번역본, `--source`를 원문으로 읽고 번역본 점검을 한다. |
| `vi` / `en` / `zh` | 없음 | 번역본만 읽고 `SOURCE_NOT_PROVIDED`를 기록한다. |

결과 JSON에는 상태, `parser_version`, 문서(번역본, 원문), 발견 항목, 번역본 점검 결과가 들어간다. 문서 본문이 들어가므로 출력 폴더(`out/`)는 `.gitignore`에 넣는다.

종료 코드: `OK`는 0, `REVIEW_REQUIRED`는 1, `FAILED`와 사용법 오류는 2다.

```
pyproject.toml
constraints.txt              테스트를 돌려 본 정확한 버전
.gitignore
.gitattributes               tests/fixtures/**/*.md 의 줄 끝을 LF로 고정한다
config/example.env           자리표시자만 둔다
app/
  models/
    document.py              문서, 요소, 위치 정보

  parsing/
    reader.py                파일 → 줄 목록, sha256
    line_parser.py           줄 목록 → 요소 목록
    tokens.py                토큰 추출, 숫자 표기 해석
    translation_check.py     짝짓기와 토큰 비교
    quality.py               발견 항목 → 결과 상태

    __main__.py              명령줄
tests/
  fixtures/rag_ko/           한국어 샘플
  fixtures/rag/              가상 원문(영어, 베트남어, 중국어)

```

의존성은 Pydantic뿐이고, 개발용으로 pytest와 ruff를 쓴다. Python 3.10에서 동작해야 한다(D-003). 도입할 버전이 Python 3.10을 지원하는지와 라이선스를 확인하고 버전을 고정한다(D-009). `pyproject.toml`에는 범위를 두고, 정확한 버전은 `constraints.txt`에 둔다. 확인한 내용은 구현 계획의 Task 1에 있다.

|---|---|
| 파싱 규칙 | §5의 규칙과 "추측하지 않는 지점"마다 몇 줄짜리 입력으로 확인한다. |
| 샘플 기준값 | 한국어 샘플이 요소 49개(§2 완료 기준 1)로 읽힌다. 3.2 표가 `e0017`, 9페이지, 경로 `["3", "3.2"]`, 36~42줄이다. `합께`, `패덜`이 그대로다. 영어·베트남어·중국어 원문도 같은 개수로 읽힌다. |
| 줄 누락 없음 | 빈 줄이 아닌 모든 줄이 정확히 한 요소에 속한다. 샘플과 깨진 입력 모두에 적용한다. |
| 번역본 점검 | 원문 세 벌 각각과 한국어 샘플의 짝이 모두 `match`이고 상태가 `OK`다. 테스트 안에서 번역본을 코드로 변형해, 예상한 코드가 예상한 요소 ID에 붙는지 확인한다: 숫자 바꾸기와 단위 바꾸기 → `TOKEN_MISMATCH`, 표 행 삭제 → `TABLE_SHAPE_MISMATCH`, 문단 삭제 → `SEGMENT_UNALIGNED`, 헤딩 삭제 → `SKELETON_MISMATCH`. |
| 숫자 표기 | 사례 표로 확인한다: 베트남어 `1,5` = 1.5, 베트남어 `1.000` = 1000, 영어 `1,000` = 1000, 전각 숫자, 표기에 맞지 않는 숫자의 문자열 비교, `NUMBER_FORMAT_AMBIGUOUS`. |
| 깨진 입력 | 빈 파일, 없는 파일, UTF-8이 아닌 파일 → `FAILED`. 페이지 마커 없음, 열 수 불일치 → `REVIEW_REQUIRED`. BOM, CRLF → 정상. 예외가 밖으로 나가지 않는다. |
| 명령줄 | 종료 코드 0/1/2. 출력 JSON이 모델로 다시 읽힌다. 원문 없이 번역본만 주면 `SOURCE_NOT_PROVIDED`와 종료 코드 1이 나온다. 로그에 샘플 본문 문장이 없다. |

테스트 데이터는 가상 데이터다(D-014). 원문 세 벌은 한국어 샘플과 줄 단위로 대응하도록 썼고, 베트남어 파일만 소수점 쉼표(`±1,0%`)를 쓴다.

### 사내 확인

테스트로는 실제 변환 산출물의 표기와 D-008의 가정을 확인할 수 없다. 구현 뒤 사내에서 실제 파일 쌍 몇 건에 명령줄을 실행하고, 발견 항목 코드별 **개수만** 가져온다. 본문과 결과 JSON은 가져오지 않는다. 미분류나 `SEGMENT_UNALIGNED`, `NUMBER_FORMAT_AMBIGUOUS`가 많으면 규칙을 고치고 `parser_version`을 올린다.

## 11. 미결

- 번역기가 숫자 표기를 바꾸는지(베트남어 `1,5`가 번역본에 `1,5`로 남는지 `1.5`로 바뀌는지, 글자로 쓴 수가 숫자로 바뀌는지). 사내 확인에서 본다.
- 원본 → `rag.md` 단계의 오독을 검출할 수단이 없다.
- 이미지가 있는 구간의 판정을 어떻게 다룰지. 단위 ④에서 정한다.
- 한계 표현의 언어별 대응표. 실제 파일 쌍을 본 뒤에 만든다.
- 일본어 문서가 여전히 대상에 포함되는지.
- 원문에만 있는 요소 때문에 생긴 `SEGMENT_UNALIGNED`는 번역본 쪽 요소가 비어 있어, 번역본에서 막을 요소가 없다. 이 경우를 판정에서 어떻게 다룰지. 단위 ④에서 정한다.
- Python 3.10에서만 설치되는 `exceptiongroup`과 `tomli`의 버전은 확인하지 못했다(사외 PC에 Python 3.10이 없다). 사내 확인에서 본다.
